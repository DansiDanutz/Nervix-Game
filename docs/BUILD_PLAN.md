# Nervix World: build plan from current state to DONE

Repo: `/Users/davidai/Sandbox/deepseek-harness-workspace/nervix-world-city-slice` (branch `feat/merchant-city-slice`). I worked read-only and spot-checked the riskiest audit claims myself:
- `presence.mjs:45` trusts the `userId` the client sends.
- `POST /merchants/provision` uses `body.userId` (`index.mjs:222-223`).
- `POST /orders` calls `ensureMerchant` with body ids and sends client prices to `createOrder` (`index.mjs:643-655`).
- The `const order` reassignment bug is at `index.mjs:664/671`.
- `speechSynthesis` is still used at `app/src/ui/AgentPanel.tsx:45-47`.

Two facts shape the whole plan:
- **`server/src/index.mjs` is a hotspot.** It is 865 lines with 61 routes, above the 800-line ceiling, and almost every milestone would edit it. `store.mjs` (572 lines), `slice-fixtures.mjs` and `route.spec.ts` are shared in the same way.
- **On the client, `App.tsx` and `SceneView.tsx` are shared too**, and so is `blender/scenes/nervix_city_slice_01.blend`. The visual workflow is editing all three right now.

So the plan starts with two behaviour-preserving "seam" milestones (F0 for the server, F1 for the client). After those, parallel milestones own separate files.

## (b) Ordered milestones

### Conventions that bind every milestone

- **Slice-file token.** At any moment exactly one milestone holds the `nervix_city_slice_01.blend` token, together with `export_arrival_slice.py`, `arrival_*.py` and `app/public/slice/manifest.json`. The order the token passes in is: V0 (now) → V1 → B2 → V2 → V3 → V4 → B5 → V5.
- **Kit `.blend` files.** Each kit is a new file with exactly one owner. Kits may open the slice `.blend` read-only to append materials.
- **District check.** Every Blender milestone records the district `.blend` sha256 before and after, and the two must match.
- **Shell token.** At most one running milestone may edit `App.tsx`, `SceneView.tsx` or the F1 registries (`app/src/features/registry.ts`, `app/src/ui/PanelHost.tsx`). Every other milestone adds its own files and asks the lead to add a one-line registration when it merges.
- **Migration numbers are reserved up front**, so two milestones never both write `016`:
  - 016: conversations per user (S3)
  - 017: plots (B1)
  - 018: listing display (P1)
  - 019: presence settings (C9)
  - 020: district plots (B5)
- **Shared docs.** Only the lead edits `PROGRESS.md`, `ACCEPTANCE.md`, `STATUS.md` and `SETUP.md`, at milestone merge. Workers hand over the text.
- **E2E runs are serialized.** All runs share ports 28797 and 25183 and the single GPU. Use one lock, or the per-run ports that F1 makes configurable. Every milestone gets its own spec file, and no milestone appends to `route.spec.ts`.
- **Standard proof**:
  - `cd server && node --test`
  - `cd app && pnpm exec tsc --noEmit && node --test src/**/*.test.ts`
  - GPU Playwright with fixtures (`PW_GL=metal`)
  - Visual milestones also need the strip reference | Blender | game, using the A01 camera from V1.

#### F1 handoff notes (binding for later milestones)

- **Two place ids, on purpose.** `placeKey()` in `app/src/world/place.ts` keeps the legacy DOM/test values (`plaza`, `venue`, `house:<doorId>` with `bld_*` door ids) only for `data-place` and `__nervixPlace`, so the existing specs do not change. `placeId()` returns the shared contract ids (`plaza`, `openpoker`, `prop_*`) from `shared/contracts/place-ids.json`. C3, P3 and any server-facing code use `placeId()`, never `placeKey()`.
- **playerState and the typing filter are not wired yet.** `PlayerController.tsx` still has its own `typing` check (without SELECT) and does not call `playerState.publish`, so `playerState.ref.current` stays at `INITIAL_PLAYER` at runtime. CT1 owns that hookup: publish position, yaw and speed in the frame loop and use `isTypingTarget` from `app/src/input/keys.ts`. C3 does not read yaw from `playerState` until CT1 lands.
- **E2E ports.** `app/e2e/ports.ts` (`e2ePorts()`) reads `E2E_API_PORT`, `E2E_WEB_PORT` and `E2E_DB`. `prepare-db.mjs` uses it through `app/e2e/helpers/` (database, schema and fixtures steps). `playwright.config.ts` still hardcodes the ports and database, and the lead applies that hookup (the fidelity workflow owns the file). Until then, a per-run port override is not in effect and E2E stays serialized under one lock.
